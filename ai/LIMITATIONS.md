# AI/Modeling — Limitations & Design Notes

This document exists so the team (and judges) know exactly what this
system does and does not claim to do.

## What this is

A lightweight, rule-based behavioral modeling system. Sensor readings
(light, temperature, humidity, motion, noise) are turned into a small
set of engineered features, and a set of hand-assigned weights map
those features to a distribution across five "future state" categories.

## What this is NOT

- **Not a trained ML model.** The scoring weights in `scoring/score.py`
  were manually assigned based on reasonable assumptions about how each
  signal relates to each future-state category. They were not learned
  from labeled behavioral data.
- **Not a real prediction of anyone's future.** The five "future
  states" are a narrative/UX device, not a scientific forecast.
- **Not a direct measurement of focus, productivity, or mental state.**
  The sensors measure indirect environmental proxies — ambient light,
  noise level, motion, temperature, humidity — nothing more.

## Synthetic data policy

- All synthetic data is generated by `data/synthetic.py` and is always
  explicitly flagged with `is_simulated: true` on every record.
- `service.py` propagates that flag through to `behavioral_features`,
  `predictions`, and API responses — a record is never silently mixed
  between real and synthetic origin.
- Synthetic data exists purely to unblock development and testing
  before real sensor data is flowing. It is not meant to appear in the
  live demo once real data is available.

## Validation strategy

Covered in `tests/test_scoring.py`, run with `python3 -m tests.test_scoring`
from inside `ai/`. It checks:

- Scores always sum to exactly 100 across all five synthetic behavioral
  profiles.
- No crashes or invalid output on edge-case input: all-zero motion,
  maxed-out noise/light, minimum values across the board, and a
  single-sample window.
- What-If (single and multi-feature) produces a visibly different
  result than the baseline, and always still sums to 100.
- Passing an unknown feature name to What-If raises a clear error
  instead of failing silently.

This confirms the model is **robust** (doesn't crash, always
normalizes correctly). It does not yet confirm the model is
**calibrated** — the weights are a first-pass design choice and will
be retuned once real sensor data is available.

## Known open item

Weight calibration is ongoing. An early version of the weights relied
almost entirely on within-window *variance* (e.g. "how stable was the
light"), which meant a window of constantly-maxed sensor readings and
a window of constantly-minimum readings could score nearly
identically, since both have zero variance. This has been partially
addressed by adding average-signal-level weights alongside the
variance-based ones, but further tuning against real data is expected.
